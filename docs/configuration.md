# Конфигурация и Hot Reload

Каталог `config/` содержит плоские TOML-файлы. Его можно заменить через
`POLAR_CONFIG_DIR` **до запуска процесса**. Отсутствующий файл означает все
значения по умолчанию. Пустой существующий файл считается незавершённой записью.
Неизвестные ключи, неверные типы и значения вне диапазона
отклоняются. При ошибке продолжает действовать последняя корректная версия всего
набора файлов. Проверка чтения и пауза 0,2 с после изменения защищают от обычной
записи файла по частям; для надёжного обновления записывайте временный файл и
переименовывайте его в `*.toml`. Если одновременно обновляются несколько файлов,
публикуйте их до истечения паузы. Независимые корректные изменения файлов могут
образовать промежуточную версию.

Наблюдатель запускается один раз в процессе при первом доступе к настройкам
(в том числе при старте API или pipeline),
проверяет файлы каждые 0,5 с и останавливается при закрытии API. В Notebook
повторный вызов не создаёт второй поток; для явного завершения вызовите
`app.configuration.manager().close()`. Для принудительной проверки после
редактирования доступен `manager().reload(force=True)`; он применяет только
корректную версию. После нового запуска приложения перечитываются также
статические параметры.

## Приоритет

1. Значение по умолчанию в схеме `app/configuration.py`.
2. Соответствующий TOML-файл.
3. Существующие переменные окружения из таблицы ниже. Окружение фиксируется при создании менеджера; для изменения работающего
   сервиса нужен перезапуск процесса. Изменения окружения родительского shell
   не передаются уже запущенным процессам.
4. Явные аргументы конкретного задания (`MainPipelineConfig`, `main(...)`,
   параметры API-запроса), где они предусмотрены.

Значения научных вычислений и загрузок закрепляются в начале pipeline или при
приёме задания API. HTTP-запрос видит одну версию конфигурации. В SQLite-очереди
снимок хранится в `job_config`, а у запущенного задания копия без секретов
записывается в `<data-root>/jobs/<job-id>/effective-config.json`. Для обычного
pipeline снимок и явные параметры задания находятся в
`<plots-base-dir>/<date>/effective-config.json`. Изменение TOML во время работы
задания применяется лишь к новым заданиям. Повторный запрос с тем же телом,
но другой конфигурацией создаёт отдельную запись очереди.
При создании API с явно переданным `Settings` этот объект считается явной
фиксированной настройкой приложения; для Hot Reload backend-полей используйте
обычную фабрику `create_app()` без аргумента `settings`.

## Доступные параметры

`D` — динамический (действует без перезапуска), `N` — для новой операции,
`S` — статический (нужен перезапуск). Числа целые, границы включены.

| Файл / ключ | По умолчанию | Допустимо | Режим | Используется |
|---|---:|---|:---:|---|
| `backend.toml` `root` | `files` | непустой путь | S | Хранилище API и каталог данных pipeline по умолчанию |
| `backend.toml` `render_assets` | `files/render-assets` | непустой путь | S | Ресурсы рендеринга карт |
| `backend.toml` `cors_origins` | `[]` | список непустых строк | S | CORS и приём frontend-логов |
| `backend.toml` `max_samples` | 200000 | 1…10000000 | N | Лимит временного ряда |
| `backend.toml` `max_cells` | 1000000 | 1…100000000 | N | Лимит таблиц и кеограмм |
| `backend.toml` `max_points` | 2000000 | 1…100000000 | N | Лимит карты |
| `backend.toml` `max_response_bytes` | 67108864 | 1024…1073741824 | N | Размер ответа |
| `backend.toml` `max_days` | 31 | 1…3660 | N | Длина диапазона запроса |
| `backend.toml` `job_timeout` | 1800 | 1…86400 с | N | Таймаут новых worker-заданий и блокировок |
| `backend.toml` `job_workers` | 2 | 1…64 | D | Число одновременно запускаемых worker-процессов |
| `backend.toml` `max_jobs` | 32 | 1…100000 | D | Приём новых заданий в очередь |
| `logging.toml` `directory` | `logs` | непустой путь | S | Каталог логов |
| `logging.toml` `frontend_level` | `INFO` | DEBUG, INFO, WARNING, ERROR, CRITICAL | D | Браузерный логгер (опрос API каждые 5 с) и серверный приём |
| `logging.toml` `backend_level` | `INFO` | те же уровни | D | Backend-логи |
| `logging.toml` `pipeline_level` | `INFO` | те же уровни | D | Pipeline-логи |
| `logging.toml` `max_bytes` | 20971520 | 1024…1073741824 | D | Ротация логов |
| `logging.toml` `retention_days` | 30 | 1…3650 | D | Срок хранения архивов |
| `logging.toml` `console` | true | true/false | D | Вывод в stderr |
| `logging.toml` `files` | true | true/false | D | Запись файлов |
| `pipeline.toml` `plots_base_dir` | `results` | непустой путь | N | Каталог результатов новых запусков |
| `pipeline.toml` `observation_source` | `aurorasaurus` | `aurorasaurus`, `spaceweatherlive` | N | Источник наблюдений новых запусков |
| `downloads.toml` `simurg_timeout` | 30 | 1…600 с | N | Таймаут нового SIMuRG-клиента |
| `downloads.toml` `simurg_polling_interval` | 60 | 1…3600 с | N | Интервал опроса нового SIMuRG-клиента |
| `downloads.toml` `simurg_map_polling_interval` | 5 | 1…3600 с | N | Интервал опроса SIMuRG-карт в backend |
| `plotting.toml` `dpi` | 300 | 30…1200 | N | `set_plt_def_params` и `set_constructor_def_params` |

Режим `D` для `job_workers` действует на новые запуски worker-процессов;
уже работающие задания не прерываются. `max_jobs` проверяется при отправке нового
задания. Остальные лимиты `N` берутся из версии, закреплённой HTTP-запросом.

`POLAR_DATA_ROOT`, `POLAR_RENDER_ASSETS`, `POLAR_CORS_ORIGINS`, `POLAR_LOG_DIR`,
`POLAR_LOG_FRONTEND_LEVEL`, `POLAR_LOG_BACKEND_LEVEL`,
`POLAR_LOG_PIPELINE_LEVEL`, `POLAR_LOG_MAX_BYTES`,
`POLAR_LOG_RETENTION_DAYS`, `POLAR_LOG_CONSOLE`, `POLAR_LOG_FILES`
перекрывают одноимённые настройки. `POLAR_API_KEY` и `SIMURG_EMAIL` остаются
только переменными окружения. Снимки, TOML-файлы и публичный endpoint не содержат
эти значения. `VITE_API_BASE_URL` и `VITE_MOCK_API` остаются параметрами сборки
frontend; их изменение требует новой сборки. `VITE_LOG_LEVEL` используется как
начальный уровень до первого успешного получения `/api/v1/config/public`.
Явные аргументы `SimurgClient` перекрывают настройки загрузки. `plotting.dpi`
задаёт общие стили Matplotlib после вызова функций `plot_settings`; явный DPI
конкретного графика (например, `SolarDiskConfig.dpi`) остаётся параметром задания.
Числовые константы научных алгоритмов, схемы продуктов, URL источников и
параметры отдельных визуализаций не перенесены: они задают расчёт или уже
передаются явно конкретным заданием. Их изменение требует отдельного изменения
алгоритма либо явного параметра задания.

Пример безопасного изменения уровня в работающем API:

```bash
cp config/logging.toml config/logging.tmp
sed -i 's/backend_level = "INFO"/backend_level = "DEBUG"/' config/logging.tmp
mv config/logging.tmp config/logging.toml
```

Изменение `backend.root`, `render_assets`, `cors_origins` или
`logging.directory` будет зарегистрировано как требующее перезапуска. До него
продолжает действовать старое значение. Перемещение хранилища требует отдельной
операции с файлами; смена пути в конфигурации их не переносит.

## Отдельный worker

API и worker независимо наблюдают общий TOML. Новые лимиты `long_job_timeout`,
`job_max_attempts`, `external_wait_timeout`, защищённая диагностика двух процессов
и правила миграции описаны в [worker.md](worker.md).
